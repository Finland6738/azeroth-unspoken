# 0008. LF line endings in all text files

- Status: Accepted
- Date: 2026-10-29 (commit `79c23f3`, "Fine riga LF per tutti i file di testo", in Italian)

## Context

Development happens on Windows, where git can convert line endings to CRLF depending on the local configuration (`core.autocrlf`) and on each tool. With several sessions and several machines involved, the same line can end up different depending on who saved it, and diffs fill up with changes that are not changes. The WoW client reads LF and CRLF indifferently, but scripts, tests and review tools benefit from a single convention.

## Decision

- **All text files in the repository use LF**, regardless of the system. This is enforced by `.gitattributes`:
  ```
  * text=auto eol=lf
  ```
- **Exception**: Windows command files (`*.bat`, `*.cmd`) stay CRLF, because Windows requires it.
- **Binary files are declared** (`*.tga`, `*.blp`, `*.png`, `*.jpg`, `*.ogg`, `*.mp3`) so that they are not touched.
- Editors must be set to save with LF (in WebStorm, in the code style settings, line separator "Unix and macOS"), without a BOM.

## Alternatives considered

- **CRLF everywhere.** Consistent with Windows, but inconvenient for Unix tools, for `git diff` on other systems and for people contributing from Linux or macOS.
- **Leaving `core.autocrlf` to each person.** This is exactly what generates noisy diffs.
- **Converting only through `.editorconfig`.** Not enough: git must also normalize files created by tools that do not read it.

## Consequences

- Positive: clean diffs, no surprises between machines, scripts and tests that do not have to handle `\r`.
- Negative: on Windows git may warn that a file "will be converted" at the next commit; just let it happen. Files generated by tools that write CRLF are normalized at commit.
- Whoever adds a new file type that must not be touched (for example an image in a format that is not listed) declares it `binary` in `.gitattributes`.
