# 0028. World variables: weather, day and night, subzones, quests, reputation, rest and flight

- Status: Accepted
- Date: 2026-10-30 (phase R3 of the roadmap after the analyses A1 and A2, tracking issue #131; issues #92, #93, #94, #95 and #121)

## Context

The offline analyses found that the client tells the addon many things it did not use: the weather, whether it is day, the subzone, the quest log, the reputation levels, whether the character rests and whether it is on a flight path. Until now the narrator knew only the zone, the hour read from fixed thresholds (dawn 5-8, day 8-18, dusk 18-21), and the quest events used by the relationships. Lines like "the first visit, in the rain", "dusk in a forest", "you enter an inn", "the flight begins" could not be written.

None of these APIs has been tried in the real client: `/au probe` (#82) exists, the owner has not run it yet. So every reading must be guarded by Compat and the narrator must work, unchanged, when a reading is missing, restricted or incoherent ([ADR 0005](0005-compat-secret-values-and-defensive-events.md)). Regional packs load on a change of continent ([ADR 0025](0025-language-and-regional-packs-loaded-on-demand.md)): a subzone event must never cause a load. The archive ([ADR 0027](0027-sqlite-authoring-archive-and-exporter.md)) must keep an empty round trip, so the new conditions and lines live in the same places as the old ones.

## Decision

1. **One module, `Systems/World.lua`, and thin readings in `Core/Compat.lua`.** Compat gets `Weather()`, `IsDayTime()`, `OnTaxi()` and `PlayerPosition()`; each returns "unknown" (`"unknown"` for weather, `nil` for the others) when the API is missing, raises an error, answers with a secret value or answers something incoherent. The module `World` keeps a small state (session only). It registers its own sources for `WEATHER_CHANGED`, `DIEL_CYCLE_CHANGED`, `ZONE_CHANGED`, `ZONE_CHANGED_INDOORS`, `PLAYER_UPDATE_RESTING`, `PLAYER_CONTROL_LOST`, `PLAYER_CONTROL_GAINED`, `QUEST_LOG_UPDATE`, `QUEST_REMOVED` and `UPDATE_FACTION` (normalized as `WEATHER_CHANGE`, `DIEL_CHANGE`, `SUBZONE_ENTER`, `REST_CHANGE`, `CONTROL_LOST`, `CONTROL_GAINED`, `QUEST_LOG_CHANGED`, `FACTION_UPDATE`), and it listens to `QUEST_STATE`, the event that `Systems/Relationships.lua` already published for `QUEST_ACCEPTED` and `QUEST_TURNED_IN`. That event now also carries the quest id: **the quest events are extended, not duplicated** (a second source for the same client event would replace the first).

2. **Unknown is never a value.** `ctx.weather` is `"unknown"`, and `ctx.isDay`, `ctx.onFlight` and `ctx.quest` are `nil`, when the reading fails. A condition on a reading that is unknown is **false for `true` and for `false`** (`dayTime`, `onFlight`, `questActive`, `questReady`; `weather = "clear"` does not match `"unknown"`). A line that names the weather or the flight carries the condition, so with the API unreadable it is not chosen, and the rest of the content is unchanged. Two cautious readings of the weather: a type the enum does not have is unknown, and a type that says rain with intensity 0 is unknown (never "clear").

3. **Weather** (#92). The type is read by the **name** of the `Enum.WeatherType` value (the values are not in the API dump): the words `rain`, `snow`, `storm`, `sand`, `fog` and `clear` in the name are recognised, anything else is unknown. `ctx.weather` is read each time the context is built. The event `weather_change` fires when the weather has changed and **stayed changed for 3 seconds** (a flickering rain makes no event); the first reading of the session is the starting point, not a change, and so is the reading after a loading screen. It is silent in combat and for six seconds after a loading screen: the `zone` event speaks then, and its lines can ask for `weather` ("arriving in the rain"). The validator warns when a text names the weather (a short list of words, English and Italian) and the rule has no `weather` condition. It checks only the events that describe the surroundings, and not rules tied to a place (`mood`, `zone`, `subzone`, `place`), so the "snow" of a snowy zone or the "thunder" of a battle cry are left alone.

4. **Day and night** (#93). `ctx.isDay` is `C_DateAndTime.IsDayTime()`. `ctx.time` keeps its four values: **night is what the client says** is night; during the day, **dawn** and **dusk** are the transition hours, two hours after and before the last change seen in the session (`DIEL_CYCLE_CHANGED` calibrates them), and the fixed hours 5-8 and 18-21 until a change has been seen. With no answer from the client the old thresholds are the **fallback**, exactly as before (`time` conditions keep working). The events `dawn` and `dusk` fire on `DIEL_CYCLE_CHANGED`; without that event a 60-second poll of the hour fires them at the thresholds. The event carries `time = dawn|dusk` so its lines can ask for it although the flag has just flipped.

5. **Subzones and landmarks** (#94). `ZONE_CHANGED` and `ZONE_CHANGED_INDOORS` are sources for `SUBZONE_ENTER`. The event `subzone_enter` is offered when the subzone has changed and **stayed for 2.5 seconds** (a flickering border makes one event at most), is not empty (leaving to open ground says nothing), is not the same one within 10 minutes, and is not in combat or in the first six seconds after a loading screen. **A subzone event never loads a pack**: packs listen to `WORLD_ENTER` and `ZONE_ENTER` only, and a test counts the `LoadAddOn` calls over many subzone changes, with the packs installed as in the client. A **landmark** is a named place inside a subzone (`Data/Landmarks.lua`, `NS:RegisterLandmarks`): `id`, `zone`, `subzone`, `tags`, and optionally `mapID`, `x`, `y`, `radius`. A landmark with coordinates is recognised only when the client gives the position (`C_Map.GetPlayerMapPosition`, never in instances) and the player is inside the radius; without coordinates it is recognised by the subzone name. When the subzone is a landmark the event is `landmark` instead of `subzone_enter` (one event for the moment). The hierarchy is continent (`Data/Places.lua`) > zone > subzone > landmark; the data are validated at load and by `/au validate` (duplicate id, missing subzone, coordinates outside 0-1, radius without coordinates). Names are from the English client and not yet checked in Forever; a wrong name only means the place is not recognised and `subzone_enter` speaks. The condition is `landmark = "<id or tag>"`, the placeholder is `{landmark}` (the name the client gives; a line with it is not composed without a landmark).

6. **Quests and reputation** (#95). Quest ids and numbers only, in memory, for the session. The title stays in the snapshot of the log for debugging; **no quest text** is read except the objectives' `finished` and `numFulfilled` numbers, and nothing is saved. `quest_progress` fires when an objective is finished or a quest becomes ready for turn-in (one event per reading, the ready one first); single kills are not events. `quest_complete` fires on `QUEST_TURNED_IN` and works even without `C_QuestLog`. The attempts of a quest are the times it was accepted in the session (unknown if it was accepted before): `questAttemptsMin = 3` is "after many attempts". Reputation: only the **standing** (`hated` to `exalted`, from `FactionData.reaction` 1-8) of each faction; `reputation_change` fires when a standing changes, never for points inside a standing; the first reading is the starting point; no faction name enters a line. `quest_complete` and `reputation_change` have the Director priority 2 (above the ordinary atmosphere, below the exceptional events); the other new events are ordinary atmosphere.

7. **Rest and flight** (#121). `rest_enter` fires when `IsResting` turns on and stays on for 2 seconds, not at login or after a loading screen (the flag that comes with the city is the starting point), and not in combat. `journey` has two stages: **start** (after `PLAYER_CONTROL_LOST`, 0.8 seconds later `UnitOnTaxi` says true: a fear or a stun is not a flight) and **arrival** (control gained and `UnitOnTaxi` false, or a loading screen; only if the flight lasted at least 20 seconds). A zone change in the middle of a flight does not end it. Conditions: `onFlight`, `journey = "start"|"arrival"`, `journeyMin = <seconds>` ("a long journey"). Without `UnitOnTaxi` there is no flight.

8. **Director.** All new events are candidates of the Narrative Director: its gate, pacing, budget and die decide. `weather_change`, `dawn`, `dusk`, `subzone_enter`, `landmark` and `journey` belong to the module `world` (switched off with it); `quest_*`, `reputation_change` and `rest_enter` are personal. Categories: `exploration` for the world events (budget 4 per ten minutes, 30 seconds between two), `life` for the rest. Each event has its own default chance and cooldown (`weather_change` 300 s, `dawn` and `dusk` 600 s, `subzone_enter` 120 s, `landmark` 180 s, `quest_progress` 120 s, `quest_complete` 60 s, `reputation_change` 120 s, `rest_enter` 600 s, `journey` 120 s); the user's `/au chance` wins.

9. **Archive.** The rules (`Data/RegistryWorld.lua`) and the texts (`AzerothUnspoken_enUS/World.lua`, `AzerothUnspoken_itIT/World.lua`) follow the layout the importer reads. The conditions are JSON data like the others, so `tools/archive/` needs no change, and the round trip of the new files is an empty diff (the test of ADR 0027 covers them: 891 intentions are archived now). The condition keys are **not** dimensions of the selection index (ADR 0024): a rule that asks only for `weather` or `landmark` is in the generic group of its event, in the engine and in the archive alike. The landmark data stay in `Data/Landmarks.lua`, like `Data/Places.lua`: they are data of the engine, not content of the archive.

## Alternatives considered

- **Rebuild `ctx.time` from `IsDayTime` only.** It would lose dawn and dusk, which the existing lines and the index use. The client gives two values, the narrator uses four.
- **A new bus source for the quest events.** `AddSource` replaces the earlier definition of the same client event; the relationships would have lost theirs. Extending the payload is safe.
- **Fire `weather_change` at once.** The weather flickers; a three-second settle and a cooldown cost nothing.
- **Make `landmark` and `subzone_enter` two candidates.** They would compete in the arbitration of the same moment; one event with the better name is simpler.
- **Make `landmark`, `weather` and the rest dimensions of the index.** It would change the selection index, which the parallel selection work (#89, #90, #91) may change. They can become dimensions later without touching the content.
- **Save the quest attempts.** Ids and counts could be saved (never text); this is not needed for a first set of lines, and the session value is honest ("unknown" otherwise).

## Consequences

- Positive:
  - The narrator can say the rain, the dusk, the inn, the flight and the quest done after many tries: 63 new intentions in English and Italian, at least two variants each.
  - With the APIs unreadable the narrator behaves as before: the tests remove each API in turn.
  - No new road to public chat, no quest or chat text read or saved, no pack loaded by a subzone.
- Negative or costs:
  - Every value is a hypothesis until `/au probe` and the checklist R3b are run in the client: the enum names of the weather, when `DIEL_CYCLE_CHANGED` fires, the payloads of the quest events, the standing numbers of `FactionData.reaction`, the order of the events in a flight, `C_Map.GetPlayerMapPosition`.
  - The calibration of dawn and dusk waits for the first change of the session; until then they are the fixed hours.
  - `ctx.weather` costs one API call each time the context is built.
  - The weather warning of the validator is a heuristic with a short list of words; it can miss a word and, rarely, warn on an image.
